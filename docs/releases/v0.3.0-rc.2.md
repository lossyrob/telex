# v0.3.0-rc.2: simpler Windows Copilot bridge access

Candidate preparation; this document does not assert publication or completed
release gates.

## What changes

Windows external-producer files now use the surrounding profile's permissions
without Telex reinterpreting their owner or ACL entries. This fixes RC1's
rejection of inherited read/execute grants. The three Node bridge files are
byte-identical to RC1: no extra PowerShell/.NET process, native compilation,
execution-policy workaround, ACL pinning or staged module activation is needed.
An already-loaded RC1 bridge can stay loaded without a reload for this change.

The CLI and daemon consistently use the producer reader for identity capture,
liveness, delivery and recovery. Regular non-reparse files, bounded reads,
same-handle metadata, daemon-side containment, derived pipe names and server
peer verification remain. Telex-owned daemon capabilities/intents and Unix
producer permissions retain their strict checks.

**Known security tradeoff:** a principal able to read a Windows registry file
learns its bearer secret. If it can also write to that session's pipe, it can
inject prompts into the Copilot session. No confidentiality from foreign
readers, sandbox isolation or explicit remote-pipe rejection is promised.
Foreign-writable files permit disruption and, with control of a same-user
server at the derived endpoint, producer impersonation. This release trusts
the workstation/profile boundary; server identity checks do not authenticate
incoming prompt senders.

Failed attach no longer deletes modules or the producer registry. Only this
attempt's binding and pending-intent generation are rolled back; unrelated
addresses and pre-existing empty binding files remain. Attempt-created empty
records can remain for GC. Binding updates serialize under bounded OS-released
locks; use the matching CLI for all writes rather than concurrent RC1/RC2
attach/detach commands. See the [Windows delivery guidance](../guide/src/guides/copilot-push.md#windows-inherited-permissions-and-rc1-upgrades).

## Explicit opt-in and upgrade

After publication, select `telex upgrade --version v0.3.0-rc.2`. Fresh installers
use `TELEX_VERSION=v0.3.0-rc.2` with the tag-pinned installer; pin the plugin
marketplace to `lossyrob/telex#v0.3.0-rc.2`. Publication is prerelease/not Latest;
default install and upgrade continue selecting stable Latest.

Upgrade/restart the owning daemon through the normal coordinated upgrade
procedure: an old daemon retains RC1's strict producer reader. Resume with the
original backend/options and verify attended-push health and real delivery.
Keep INSTALL -> ATTACH -> VERIFY for fresh App sessions, use the selected
binary's full source build id, and preserve existing names/live bindings.
Actual App installer ADS and load presentation/deadlines remain unverified;
the earlier macOS App 1.1.35 experiment is not universal App support.

All five Telex targets remain; only Windows x64 includes Watcher. macOS Telex
and installer-first bridge support do not ship macOS Watcher containment.
The package/lock/plugin/marketplace identify as `0.3.0-rc.2`; console/Watcher
package versions, schema 2-3, protocol 1.5, bridge protocol 2 and Watcher metadata
are separate axes and are not bumped.

Back up before migration. Genuine v0.1.2 cannot reopen schema 3, and a binary
swap cannot undo Watcher metadata 2-to-3 migration. Preserve compatible
owner-only snapshots, installation records, executable identities and logs;
inspect post-backup sends and receiver dedupe before restoration. Never bypass
version guards or copy live SQLite without its journal state.

Required release evidence still covers immutable reviewed/merged/tag source,
all five native targets, both macOS proofs, Windows x64 Watcher archive/forward
upgrade and Linux PostgreSQL 16. Discarded helper-design fixtures do not prove
this candidate; retain actual attempts and limitations.
