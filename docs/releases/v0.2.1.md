# v0.2.1: corrective schema-3 recovery candidate

v0.2.1 prepares the schema-3 recovery release after the **unpublished** v0.2.0
tag attempt failed. This document is candidate guidance, not an announcement
that v0.2.1 has been tagged or published. A new explicit operator publication
decision is required after review and final merged-source proof.

## Why v0.2.0 was not published

The existing `v0.2.0` tag stays at
`1b9fc8f0891d6aaa620e6a40dcb0109cb8c31bbe`. Release run36734022444 passed tag
validation and four native targets but failed Windows x64 proof while Python
opened an isolated daemon capability publication: `PermissionError: [Errno 13]`.
PostgreSQL and Publish were skipped. All four owned fixture processes exited
zero and the fixture root was removed. There is no v0.2.0 GitHub release, no
withdrawn published asset set, and no authorized tag movement or retry.
The genuine upgrade baseline remains released v0.1.2.

The original error did not preserve a native Windows code. Controlled native
fixtures now show that both a sharing conflict (WinError32) and permanent
read-data ACL denial (WinError5) can become the same Python errno13.
These fixtures explain why that diagnostic was insufficient; they do not
retroactively establish the original host's cause.

## Bounded proof-harness correction

Only the proof's Windows capability-file reader changes. It uses supported
`CreateFileW`/`ReadFile`/`CloseHandle` calls, read access with shared
read/write/delete admission, checked handle closure, and explicit native
error diagnostics. It does not change daemon publication, peer authentication,
store schema, or upgrade policy.

Inside the already-owned successor's existing 15-second readiness window,
only `CreateFileW` **ERROR_SHARING_VIOLATION (32)** is retryable. The budget is
not reset. A sharing error before owned spawn is fatal. Access denied5,
delete-pending303, errno-only13, read/close failures and other errors remain
actionable failures. Missing publication retains the existing bounded wait.
If a filesystem reports a delete-pending open as access denied, it is not
silently relabeled sharing. No generic PermissionError catch is introduced.

After a successful read, the known predecessor/successor PID, start time,
instance, authenticated Status, protocol and final deadline checks still
govern acceptance. Stale publication cannot become readiness, foreign identity
still fails, and a lock that remains held exhausts the original budget.
The report records read/spawn/publication/acceptance chronology and native
errors without exposing capability tokens.

Native controls exercise exclusive sharing, permanent read-data denial,
observed delete-pending behavior, and a real file-sharing window followed by
replacement through the bounded observer. That ordering control uses synthetic
daemon/Status identities; it is separate from genuine old/candidate process
proof. Windows x64 and ARM64 Release jobs execute these controls in addition
to the normal runtime proof.

## Recovery behavior and limits retained

The candidate contains the already-merged Windows `TOKEN_USER` alignment repair
(#154 / PR #158) and PostgreSQL query/LISTEN reset recovery (#155 / PR #156).
It supports schema3 and protocol1.5 while genuine released v0.1.2 supports
schema2/protocol1.4. The [historical candidate notes](v0.2.0.md) retain the
full included-behavior and credential-limit description.

After a future authorized publication, use the old owning image's ordinary
`telex upgrade --version v0.2.1` path, allow its authenticated drain to reach
process exit, and explicitly reattach wanted addresses with the new image.
Back up before schema migration. Keeping `previous=v0.1.2` is not a downgrade
strategy: schema3 is not reversed, the old store guard rejects it, and the new
rollback guard rejects the schema2 manifest. Do not use the unpublished v0.2.0
tag as a release-discovery or compatibility baseline.

Optional `wait-backend-recovery` capability negotiation still distinguishes
legacy compatible exit1 from capable CLI/daemon exit7; protocol equality alone
does not guarantee recovery support. One-shot credential scope, external-agent
nonownership, C=2 invocation-owner/reservation limits, owning-host drain and
potentially beyond-three-second FAILED_HELD remain unchanged. Windows
JOB-TERMINAL still does not prove every former descendant/kernel/driver object
or previously issued external I/O has finished.

## Required evidence and exclusions

The readiness packet must identify the actual reviewed and merged v0.2.1 source,
all five newly built native archives/sidecars/executable identities, exact-head
CI, independent review and scoped design inspection. It must include genuine
v0.1.2 network upgrade, ordered replacement, populated schema2 migration and
schema3 reopening, both real installers, exact marked consumption, negative
controls, native error fixtures and owned cleanup, plus hosted Linux PostgreSQL.
Earlier v0.2.0/branch assets are historical, never relabeled as final evidence.

Native SQLite coverage is distinct from PostgreSQL coverage. No live Entra,
every-platform PostgreSQL, mixed-image live IPC, universal OS cleanup, every
installer default-root branch, or signing assurance is claimed. PR #138,
#152/#153, Watcher/Station runtimes, schema4, migration-policy redesign,
hardening acceptance and campaign closure remain excluded.
