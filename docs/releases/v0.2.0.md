# v0.2.0: schema-3 recovery

This release candidate restores access to schema-3 stores for users of v0.1.2
and includes the Windows token-buffer and PostgreSQL connection-reset repairs.
It is preparation material, not a published release announcement. Publication
requires the separate operator release gate and its immutable evidence packet.

## Included changes

- Schema 3 and daemon protocol 1.5, already present in the merged product.
  Released v0.1.2 supports schema 2 and protocol 1.4; its refusal to open a
  schema-3 store is intentional. v0.2.0 preserves the newer-schema guard and
  continues the existing automatic schema initialization/migration policy.
- Aligned Windows `TOKEN_USER` buffers in both SQLite identity lookup and daemon
  peer authentication (#154, PR #158). Identity, ownership, and authentication
  checks remain intact. This repair does not establish the cause of historical
  heap-corruption incidents.
- PostgreSQL query and `LISTEN` connection-reset recovery (#155, PR #156).
  Transient wait failures share a fixed 3,000 ms recovery budget with delays
  starting at 50 ms and capped at 500 ms. The original finite wait deadline
  still wins when it expires first. Permanent authentication, configuration,
  and schema failures retain actionable errors. Independent listener recovery
  leaves polling as the delivery correctness path.
- The merged Copilot App bridge lifecycle behavior distinguishes turn-idle
  from host teardown. This does not include the separate push-intent
  restoration work in PR #138.

The optional `wait-backend-recovery` capability selects recovery-aware result
handling; matching protocol 1.5 alone does not establish support. A capable CLI
and daemon produce process/out-dir exit **7** on exhausted backend recovery.
A legacy compatible CLI receives `BackendUnavailable` detail through its
existing exit **1** path. The daemon's recorded code 7 is not evidence that the
legacy process exited 7. A new CLI talking to a legacy daemon has no new recovery
or exit-7 guarantee. Required capabilities and OS peer authentication are not
weakened. See the [compatibility matrix](../design/daemon.md#optional-wait-backend-recovery-capability).

## Upgrade and downgrade

After publication, run the existing v0.1.2 installation's `telex upgrade
--version v0.2.0`. The old process downloads and checks the release archive,
probes the candidate's metadata, installs its versioned binary and schema 2..3
manifest, authenticates and drains its owning daemon, and switches `current`.
The candidate's advertised range includes the old upgrader's required schema 2;
the new binary requires schema 3. These are directional compatibility checks.

An upgrade's `draining` acknowledgement is not proof of daemon process exit.
Allow the old daemon to finish before starting the new image. Use the owning
old image for drain; do not bypass a foreign-image authentication failure with
`--skip-drain` as a normal upgrade recipe. Reattach the addresses still wanted
with the selected new binary. Durable messages survive, but in-memory membership
and excluded PR #138 push intent are not automatically restored. This is an
ordered replacement, not a zero-interruption or cross-build live-IPC guarantee.

Schema-2 stores migrate on connection; schema-3 stores can be reopened by the
candidate. Back up the store before upgrading. Once migrated, **v0.1.2 cannot
open the schema-3 store**, and the candidate rejects rollback to its schema-2
manifest. Keeping `previous=v0.1.2` or an old executable is not a database
downgrade strategy. There is no automatic reverse migration; recovery with an
older binary would require a separately restored compatible backup and
deliberate operator coordination.

Update the Copilot plugin to the same release as the binary. Do not leave old
explicit binary paths operating against the new store or daemon.

## Credential-command limits

`--password-command` is a one-shot invocation. Telex cleans up owned work within
its supported invocation scope on completion, error, or cancellation. Persistent,
escaped, or broker-launched work is outside that contract. Querying an existing
credential agent does not make that agent Telex-owned or authorize termination.

The owning process admits at most two occupied credential invocations (`C=2`);
one configured source cannot overlap itself. This bounds invocation owners and
reservations, not descendant count or all residual OS resources. Only the host
that owns credential work drains it. Logical command/wait deadlines remain
unchanged; orderly host exit uses one additional three-second cleanup budget,
not three seconds per worker. Missing receipt retains a named `FAILED_HELD`
obligation and may delay exit beyond three seconds. Elapsed time is not proof
of cleanup or an unconditional process-exit bound.

Windows uses the selected **JOB-TERMINAL** receipt: checked termination of the
exact private single-use job, zero active job processes, the exact leader's
process handle signaled, completed/closed owned I/O, checked handle release,
and native owner completion/join before eligible publication or admission
release. It does not prove that every former descendant handle is signaled or
that kernel/driver rundown, previously issued external I/O, or external
references have finished. Unix cleanup likewise applies to the supported
process-group scope, not universal descendant containment. The detailed
[credential contract](../design/daemon.md#credential-command-ownership-during-recovery)
governs these limits.

## Evidence and exclusions

The build-only Release workflow exercises genuine checksum-verified v0.1.2
assets against actual packaged candidates on Windows x64/ARM64, Linux x64, and
macOS ARM64/x64. Its native proof covers SQLite, ordered 1.4-to-1.5 replacement,
populated schema-2 migration, preexisting populated schema 3, fresh installation,
invalid candidate rejection, and fixture cleanup. A separate disposable
PostgreSQL 16 service exercises both schema paths on Linux x64. The
[release runbook](../developing/releasing.md#immutable-candidate-proof) describes
the evidence format and final-source binding.

These are required executions, not a claim that a particular candidate has
passed. The immutable readiness packet must identify successful run IDs,
source/merge SHA, every asset and executable hash, actual backend/platform
coverage, independent review/design inspection, and any remaining uncertainty.
Native assets include Entra support; this release proof does not itself
exercise live Entra authentication or PostgreSQL on every native platform.
Required CI separately covers the merged recovery and credential lifecycle
behavior. Checksums establish byte consistency, not a publisher signature.

Excluded: PR #138 station-intent restoration, issue #152 external Application
Client bootstrap/conformance, issue #153 transactional station authority,
Watcher and Operator Station runtimes, schema 4, schema-policy redesign,
Local Daemon hardening acceptance, and campaign closure. Existing Application
Client source is not a claim that the excluded production consumer path is
ready. Preparation does not authorize installed-fleet upgrades, shared database
actions, tagging, or publication.
